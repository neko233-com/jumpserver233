# 单机受控安装与升级事务

> 中文 | [English](./INSTALLATION.en.md)

原生 CLI 将已暂存的版本与固定数据目录绑定，升级前创建并复核加密快照，调用目标二进制离线加载数据，通过后原子记录版本选择。失败恢复快照和原版本选择；中断保留日志并阻止服务启动。正式运行使用 `jms update run`。这是停机升级机制，自动下载/安装调度、上线健康失败自动回滚和跨版本业务迁移验收仍待补齐。

## 前提

- 默认单机本地持久化，无外置数据库。PostgreSQL 集群不支持本流程，不能取消集群配置后操作旧本地文件。
- 先将支持升级守卫的版本部署为当前基线，成功启动一次，再完全停止服务并暂停外部守护进程的自动重启。旧程序不会遵守新守卫；存储标记缺少升级协议或已验证密钥指纹时拒绝升级。源数据必须已经初始化，不用于空目录建站。
- 按[版本暂存](./UPDATES.md#受控版本暂存)准备官方稳定包。目标清单需声明 `preflight_protocol=1`，平台/架构必须匹配当前主机。旧包仍可校验和暂存，但不能交给安装事务。
- 使用互不包含的受管版本根目录和数据目录。持续保管同一 `JMS_VAULT_KEY`（若使用外部 key）；其他环境配置和反向代理证书仍由部署方案管理。
- 升级快照口令单独保管，不放命令参数、Git、日志或流水线参数。交互输入隐藏并确认；自动化用 `--passphrase-file -` 从受保护标准输入读取，或使用私有普通文件。口令规则与[整站备份](./BACKUP.md)相同。

## 命令

```sh
jms update install-status --root /srv/jumpserver233-releases
jms update install --root /srv/jumpserver233-releases --data-dir /srv/jumpserver233/data --sha256 VERIFIED_PACKAGE_SHA256 --revision 0 --request-id upgrade-unique-001
jms update run --root /srv/jumpserver233-releases
```

首次选择修订为 `0`，成功后递增；后续传入状态返回的当前修订。首次接管可用 `--source-version` 记录基线版本，已有受管版本则自动使用实际选择的源版本。`install` 结束后不会自行启动业务服务。将正常启动命令配置为 `jms update run --root …`，它复核候选内容，再以绑定的 `JMS_DATA_DIR`、候选网页和内置构建版本启动服务器；保留部署的监听、公开来源、认证及 Vault 环境配置，强制单机模式。

相同请求 ID、目标 SHA、原始修订和数据目录返回原回执，不重做快照、预检或恢复；变更请求内容会冲突。新请求修订过期会冲突。当前相同包无变化；已有受管版本的相同版本重建、降级和改绑数据目录拒绝。首次接管通过目标离线预检检查格式，不依据 `--source-version` 声明推断迁移兼容性。最近 100 条请求回执保存在本地私有元数据中。

## 事务和守卫

1. 验证根目录、版本、数据绑定和修订，取得数据 OS 互斥锁，拒绝活动服务和未完成的恢复。
2. 持久化事务日志与数据守卫，在根目录的 `backups/TRANSACTION_ID.jmsbackup` 创建并独立复核一致性加密快照。快照不包含控制锁、事务守卫或应用程序。
3. 写入预检阶段后临时释放数据锁，执行固定摘要的目标二进制 `--check-data --upgrade-id ID`，最多两分钟。预检使用同一套默认/活动组织存储加载，检查所有组织凭据和静态网页；不监听端口、不启动采集/计划/通知、不恢复远端共享改密任务。它可能写入本地正常启动迁移或中断记录，因此仍需快照。
4. 再取得数据锁。失败使用已记录 SHA-256 和口令验证快照，恢复旧数据并保留失败内容于 `previous_data_dir`；成功先原子持久化新版本选择，再将守卫改为活动版本，最后移除事务日志。

守卫在数据卷的 `.jms233-maintenance/upgrade.json`，不进入备份。未完成事务只允许匹配事务 ID 和程序 SHA-256 的离线预检。已完成事务只允许匹配活动二进制摘要的正常启动，防止并发旧启动在锁释放后打开新版本数据。事务 ID 是本机标识，不是认证凭据；本机文件所有者和 ACL 是信任边界，任意同权限本机修改不在隔离范围内。

准备失败、无法重新取得数据锁或恢复验证失败时，事务保留为待恢复状态；不删除日志或放行服务。目标执行失败后成功回滚的 `install` 仍返回非零退出码；`install-recover` 完成恢复后返回成功，并在 JSON 中区分 `rolled_back`、`aborted` 或 `selected`。

`run` 将信号传给子进程并等待退出；12 秒内未退出会终止子进程。Windows 不保证可转发控制台中断，可能走终止路径，不能据此宣称所有平台都已完成优雅停机验收。正常停机仍需排空 SSH/作业并按平台部署方式核对。

## 中断恢复

```sh
jms update install-recover --root /srv/jumpserver233-releases
```

恢复先取得相同数据锁；仍有预检或业务进程持锁时拒绝操作，不根据超时猜测进程已死。提交点之前恢复原快照和版本；已经持久化新选择则完成提交，不把新业务写入回滚到旧快照。已记录的回滚回执也只完成收尾。重复恢复无待处理事务时返回 `unchanged=true`。

需要验证快照时，错误口令或摘要变化会保留状态并拒绝恢复；未知修订/日志、根目录归属变化和数据路径变化也会拒绝。准备阶段未执行目标时只撤销准备状态；已经发布的快照、旧版本、失败数据和无法证明归属的崩溃残留不自动删除，验证业务后再按明确保留策略处理。每次测试的归属资源另由 QA runner 清理。

快照只恢复本地数据，不能回滚远端机器已经发生的改密或命令。离线预检不执行这些远端动作；正式启动后会按现有恢复/调度规则工作。预检通过不等于监听端口、反向代理、登录授权、真实 SSH 或应用跨版本业务全部通过，部署后仍须执行相应验收。完整更新器和企业版目标继续进行，见[SSH 优先范围](./SSH-FIRST.md)。
